# OPC-玄机 · 一人公司中枢 配置管理计划（OPC-SCMP-001）

本文解决“哪些东西算配置项、怎么命名、什么时候形成基线、谁有权改、改完怎么证明没乱”的问题。它不重复开发计划的目标与排期，只回答配置管理的五个动作：**识别、控制、记录状态、审计、交付**。使用者与时机：开发在提交与发版前看第 3、4、6 章；评审在门禁与发布时看第 4、5 章；接手者在第 7 章找到唯一可信的版本入口。本文的版本号、tag、迁移编号与发布证据均来自仓库现状（Git `main`、`v0.1.0`、`migrations/0001..0005`、`docs/releases/v0.1.0.md`），不另立一套编号。

## 1. 目的与范围

### 1.1 目的

保证任何时刻都能回答三个问题：

1. **现在跑的是哪个版本？**（代码、迁移、文档、依赖是否对得上）
2. **这个版本里有什么？**（交付物清单、变更、已知限制）
3. **出问题能回到哪个已知良好状态？**（基线、tag、备份）

### 1.2 范围

| 纳入配置管理 | 不纳入（但需引用） |
| :--- | :--- |
| 源代码 `src/`、脚本 `scripts/` | 老板的业务数据、客户资料 |
| 规格 `spec/opc-xuanji/` | 外部 DSH 市场插件本体 |
| 数据库迁移 `migrations/` | 生产库运行期数据 |
| 测试 `test/` | CI 运行日志（作为证据归档，不作为配置项） |
| 文档 `docs/`（含员工分册、过程资产） | 个人笔记、临时草稿 |
| 依赖清单 `package.json` / `package-lock.json` | 模型权重文件（由运行环境管理） |
| CI/发布配置 `.github/` | 第三方服务配置（密钥不入库） |
| Bundle 装配 `cordis.patch.yml` | 生产 `.env`（只保留 `.env.example`） |

### 2.2 配置项之间的对应关系

```text
需求（SRS） ↔ 规格（spec） ↔ 接口（IRS） ↔ 代码（src） ↔ 迁移（migrations） ↔ 测试（test） ↔ 文档（docs）
```

任何一项变更，必须检查与之关联的项是否同步；不同步即视为配置项不一致，门禁不放行。

## 3. 命名与版本规则

### 3.1 版本号

采用语义化版本 `MAJOR.MINOR.PATCH`：

| 变更 | 版本位 | 例子 |
| :--- | :--- | :--- |
| 不兼容的契约/数据变更 | MAJOR | 1.0.0 |
| 向后兼容的新能力 | MINOR | 0.2.0 |
| 向后兼容的修复 | PATCH | 0.1.1 |

当前版本：**0.1.0**（初始发布）。

### 3.2 文档版本

- 文档 `version` 与软件版本解耦，用 `0.x` 递增。
- 文档状态：`草稿 → 评审稿 → 已批准 → 基线 → 废弃`。
- 进入基线必须打 tag 并在 `docs/index.md` 登记；文档修订不改历史基线，另起版本。

### 3.3 编号规则

| 对象 | 规则 | 例子 |
| :--- | :--- | :--- |
| 文档 | `OPC-<TYPE>-<3位>` | `OPC-SRS-001` |
| 需求 | `REQ-<域>-<3位>` | `REQ-VIEW-001` |
| 用例 | `UC-<3位>` | `UC-001` |
| 测试 | `TC-<域>-<3位>` | `TC-WF-001` |
| 过程资产 | `PA-OPC-<3位>` | `PA-OPC-018` |
| 迁移 | `NNNN_描述.sql` | `0005_employee_lines.sql` |
| 发布 tag | `v<semver>` | `v0.1.0` |
| 门禁记录 | `docs/过程资产/G<n>/` | `docs/过程资产/G4/` |

### 3.4 分支与提交

- `main` 为唯一长期分支，受保护。
- 功能/修复使用短分支：`feat/<主题>`、`fix/<主题>`、`docs/<主题>`、`chore/<主题>`。
- 提交信息前缀与现有历史一致：`[release]`、`docs:`、`fix:`、`chore(ci):`。
- 合并前必须通过 CI；不强制压平历史，但一个 PR 只做一件事。

## 5. 变更控制

### 5.1 变更分级

| 级别 | 例子 | 审批 | 记录 |
| :--- | :--- | :--- | :--- |
| 轻微 | 注释、文档错字、测试断言修正 | 开发自审 | 提交记录 |
| 一般 | 新增接口字段、非破坏性迁移、依赖小版本 | 项目集成者 | PR + CHANGELOG |
| 重大 | 契约不兼容、删表/改列、权限模型、审计范围 | 老板 + 评审 | IRS 修订 + G2 + PA |
| 紧急 | 线上故障修复 | 项目集成者先处理，事后补审 | 事故记录 + PA |

### 5.2 变更流程

```text
提出 → 影响分析（需求/接口/数据/测试/文档）→ 审批 → 实施 → 验证 → 记录 → 关闭
```

影响分析必须回答：

1. 改哪些配置项？
2. 是否破坏现有契约/数据？
3. 哪些测试要新增或修改？
4. 哪些文档要同步？
5. 回滚怎么做？

### 5.3 迁移变更规则

- 迁移只追加，不改历史文件。
- 编号连续，不跳号、不复用。
- 每个迁移必须能在空库与已有库上执行。
- 破坏性变更必须提供回滚脚本或明确“不可逆 + 备份要求”。
- 迁移与 DBDD、`entities.yaml` 同步，否则 G2 不放行。

## 6. 配置状态记录

### 6.1 唯一可信入口

| 想知道 | 看哪里 |
| :--- | :--- |
| 有哪些文档、什么状态 | `docs/index.md` |
| 有哪些门禁证据 | `docs/过程资产/pa-index.md` |
| 当前版本有什么 | `docs/releases/v<版本>.md` |
| 改了什么 | `CHANGELOG.md`、git log |
| 需求到测试怎么追 | `OPC-RTM-001` |
| 表结构是什么 | `docs/OPC-DBDD-001`、`migrations/` |
| 接口是什么 | `spec/opc-xuanji/api.yaml`、`docs/OPC-IRS-001` |

### 6.2 状态记录要求

- 每次门禁通过：更新 `pa-index.md`，写清证据路径与结论。
- 每次发布：更新 `docs/index.md` 的状态与基线段、`CHANGELOG.md`、发布说明。
- 每次重大变更：在 `docs/过程资产/` 新增 PA 记录，不覆盖旧记录。
- 过程资产只追加；修订以新编号登记。

## 7. 备份、恢复与归档

### 7.1 代码与文档

| 对象 | 备份方式 | 频率 | 恢复 |
| :--- | :--- | :--- | :--- |
| Git 仓库 | 远程 `origin` + 本地 | 每次推送 | `git clone` / `git checkout <tag>` |
| 发布快照 | Git tag | 门禁时 | `git archive` |
| 发布包 | Git tag + 发布说明 | 每次发布 | 按 tag 重建 |

### 7.2 数据

| 对象 | 方式 | 频率 | RPO/RTO |
| :--- | :--- | :--- | :--- |
| 业务库 | `pg_dump -Fc` | 每日 | RPO ≤ 24h、RTO ≤ 4h |
| 关键表 | 逻辑备份 `ledger`、`contract`、`stock_txn`、`conflict_queue`、`workflow_registry` | 每日 | 保留 7–30 天 |
| 审计归档 | JSONL + SHA-256 | 每日增量、每月全量 | 只追加 |
| 配置 | `.env.example` + Profile 配置文档 | 变更时 | 重新注入，不入库 |

### 7.3 归档规则

- 审计归档目录只追加，不覆盖。
- 归档文件头写 `schema_version`、`as_of`、冻结脚注。
- 删除数据必须写审计并保留删除请求记录。
- 发布 tag 不删除、不移动。

## 8. 配置审计

### 8.1 审计频率

| 时机 | 审计内容 |
| :--- | :--- |
| 每次 PR | CI 门禁 + 影响分析 |
| 每次门禁 | 对照判据抽查配置项一致性 |
| 每次发布 | 发布检查单逐项核对 |
| 每季度 | 全量配置项盘点、孤儿文件、过期文档 |

### 8.2 审计方法

```bash
# 1. 版本与 tag
git describe --tags --always
git tag --list

# 2. 规格与代码一致性
npm run spec:check
node scripts/gen-spec.mjs --check

# 3. 文档门禁
npm run docs:check

# 4. 类型与单测
npm run typecheck
npm run test:unit

# 5. 迁移完整性
ls migrations/
```

### 8.3 不符合项处理

发现配置项不一致时：

1. 记录到 `docs/过程资产/`（PA 或偏差登记）。
2. 判断以代码还是文档为准；涉及验收的必须老板知情。
3. 修复后在下次门禁复验。
4. 不静默修改历史基线。

## 9. 工具与权限

| 工具 | 用途 | 权限 |
| :--- | :--- | :--- |
| Git / GitHub | 版本控制、PR、CI、release | `main` 受保护；合并需 CI 通过 |
| Git tag | 交付快照与门禁标签 | 只读归档，不日常开发 |
| npm | 依赖与脚本 | `package-lock.json` 入库 |
| Node ≥ 24.9 | 运行与测试 | 本地/CI 一致 |
| PostgreSQL 17 + pgvector | 数据层 | 业务库/测试库分离 |
| GitHub Actions | CI | 最小权限 `contents: read` |

### 9.1 权限边界

- 仓库不保存口令；`.env.example` 只放占位。
- 生产库账号与测试库账号分离。
- 审计表应用账号只授予 INSERT/SELECT（部署期配置）。
- 发布 tag 与远程推送需老板明确授权。
