## 1. 定位与设计原则

### 1.1 一句话定位

运行在 DSH 上的一人公司中枢插件，以"中枢调度 + 专业员工矩阵 + 三级沉淀 + TS 流程固化"补全老板在财税、法务、行政、战略、项目、情报、客户、车辆、进销存上的职能短板（产品设计 §一）。

### 1.2 十一条设计原则及其需求约束

十一条原则不是宣示，每条都约束若干需求条目；实现若违反下表"对需求的约束"列，视为不满足本文档。

| # | 原则 | 对需求的约束 | 落到哪条 |
| :-- | :------------------------------ | :----------------------------------------------------------------- | :---------------------- |
| 1 | 对话即办公 | 老板入口只有一个，不暴露员工数量与流程实例；流程实例不得要求老板直接操作 | REQ-WF-003、REQ-TASK-002 |
| 2 | 一人一助理 | 公司档案 + 老板偏好画像常驻上下文；档案读取不需重复授权申请 | REQ-VIEW-002 |
| 3 | 数据不出域 | 默认本地存储；敏感任务路由本地模型；PG/PgBouncer 不监听公网 | REQ-NFR-013、REQ-NFR-016 |
| 4 | AI 不代做取舍 | 客户取舍、人员评价、重大决策只呈报事实与选项，不自动执行 | REQ-CONFLICT-003、REQ-WF-003 |
| 5 | 建议可溯源 | 税务口径、补贴标准、合同风险规则、流程版本均须标注来源与版本；计算值为参考值 | REQ-FIN-002、REQ-VEH-002、REQ-LEG-002、REQ-WF-001 |
| 6 | 插件可插拔 | 员工插件独立安装/停用，按主体类型选装；停用不影响已落库数据 | REQ-VIEW-002、REQ-NFR-021 |
| 7 | 操作可审计 | 派工、工具调用、视图访问、流程实例、老板确认全程留痕并自动归档 | REQ-AUDIT-001、REQ-AUDIT-002 |
| 8 | 注意力保护 | 主动事件按紧急度分级推送，非紧急聚合，夜间不打扰；截止日 12h 内提醒豁免夜间静默 | REQ-CONFLICT-001、REQ-TASK-002 |
| 9 | 确定性归脚本、判断归 AI、取舍归老板 | 固定步骤由 TS 流程执行；关键节点由 Verifier 评判；取舍由老板裁决 | REQ-WF-002、REQ-WF-003、REQ-WF-004 |
| 10 | 接口与实现分离 | `hub.verifier.*`、`hub.writeIdempotent`、`agent()` 为封装约定，落地须对照 DSH 实际契约核对，不一致以 DSH 为准并回写文档 | REQ-WF-009、OPC-IRS-001 §7 |
| 11 | 自动化越高，独立校验越不能省 | 生成者不评判自己产出；风险等级由硬规则而非 AI 自述；注册前有守卫；回滚承认不可逆 | REQ-WF-001、REQ-WF-004、REQ-WF-007 |

### 1.3 硬约束（违反即否决）

- 员工间不直接调用；跨域读取只经视图；写入经中枢；员工不可递归派工；中枢并行派工、串行汇总（产品设计 §2.1）。
- 流程脚本不可被模型改写；审计只经中枢统一写入；风险等级由 Registry 硬规则计算，`meta` 禁止自述（产品设计 §2.1、§8.6.9.5）。
- 敏感字段只存在于客户管家私有存储，共享数据层与中枢均不落原始值（产品设计 §2.2）。

可复制示例（需求条目命名与追溯格式，§4.3 使用）：

```text
REQ-VIEW-001                ← 需求编号：REQ-<域>-<3位>
  ├── 依据：产品设计 §2.2 + usecases.yaml UC-001
  ├── 接口：api.yaml queryView（POST /api/v1/views/{viewId}/query）
  └── 验收：AC-1..AC-3 + TC-VIEW-001
```

## 2. 范围与非目标

### 2.1 在范围内

| 域 | 内容 | 本文档章节 |
| :---------------- | :--------------------------------------------------- | :--------------------- |
| 中枢平台能力 | 视图级授权、一次性令牌、冲突冻结与裁决、审计、Workflow Registry/Verifier/诊断 | §5、§6、§7 |
| 十一条员工线 | 财税、法务、行政、战略、项目、情报、客户、车务、货栈、WBS、外宣 | §9 / 员工分册 |
| 定时自动化 | cron 任务配置与执行、每日晨报、幂等与告警、插件/关键词雷达 | §8 |
| 网页表现层 | 插件栏入口、右侧驾驶舱、会话桥/记忆桥、上传归置、雷达展示 | §8.4 |
| 非功能 | 性能、可靠性、安全合规、可运维性 | §10 |
| 数据与合规 | 补贴官方源、敏感字段、审计保留期 | §11 |

### 2.2 非目标（本版明确不做，且不得在实现中顺手做）

| 非目标 | 理由与出处 |
| :--------------------------------------- | :--------------------------------------------------------------------- |
| 字段级授权 | 授权粒度 = 视图级，"不得反查单条明细"属约定性约束而非技术强制，补偿手段见 §3.5（产品设计 §2.2 已知局限） |
| 独立向量数据库 / 独立消息队列 / 独立编排引擎 | 前置约束明确不引入（架构 §前置约束） |
| v1 部署 Redis | v1 不部署；关键写操作直接落 PostgreSQL 以幂等键保障一致性（架构 §2.5） |
| ELK / Loki / Prometheus + Grafana / APM | 可观测性走轻量方案（架构 §六） |
| Phase 1 把 `diagnose` 做成独立插件 | 诊断能力归属中枢内部能力 `opc_hub.diagnose`（产品设计 §8.6.4） |
| 高影响流程整体回滚 | 高影响（高风险）流程只做"暂停 + 人工修复"（产品设计 §8.6.9.7） |
| 把 Verifier 计入员工矩阵 | Verifier、`diagnose`、Registry、`audit`、coding agent 属平台能力，不注册业务工具、不参与派工竞争（产品设计 §三） |
| 事后修改审计表主键 | 主键 `(id, created_at)` 必须在建表期预留，不做事后改主键（架构 §5.4） |

## 3. 角色与权限矩阵

### 3.1 角色定义

| 角色 | 定义 | 权限要点 | 出处 |
| :--------------- | :--------------------------------------------- | :--------------------------------------------------- | :------------- |
| 老板 | 唯一的人类决策者 | 全视图；冲突破裁；流程观察期异常确认；手动放行 | 产品设计 §8.2 |
| 员工插件 | 函数/Subagent 形态，`inject:['opc_hub']` | 按注册声明 `required_views` 与 `write_targets` 行事；不直写审计 | 产品设计 §2.4、§8.1 |
| 兼职 / 外包 | 外部协作者 | 按模块白名单；默认禁用财税、法务、客户敏感视图 | 产品设计 §8.2 |
| 只读 | 旁观者 / 顾问 | 只读视图，不可写入、不可裁决 | 产品设计 §8.2 |
| 中枢平台能力 | Verifier / `diagnose` / Registry / `audit` / coding agent | 不注册业务工具、不计入员工矩阵、不参与派工竞争 | 产品设计 §三 |

员工插件注册时须一次性声明三张清单，示例（字段名与 `ref.employee_plugin` 一致：`required_views` / `tools` / `write_targets`）：

```json
{
  "pluginId": "opc_finance",
  "displayName": "财税管家",
  "scope": "single",
  "required_views": ["view_ar_ap", "view_project_status", "view_contract_index"],
  "tools": ["opc_finance_ledger_write", "opc_finance_ar_ap_query", "opc_finance_tax_calendar"],
  "write_targets": ["ledger", "ar_ap", "tax_calendar"],
  "enabled": true
}
```

### 3.3 敏感字段可见性矩阵

| 数据 | 存放位置 | 视图可见 | 中枢可见 | 跨域获取方式 |
| :------------------- | :--------------------------- | :------------------- | :------------- | :--------------------------- |
| 客户敏感字段 | `biz.customer_sensitive` | 不可见（仅级别标记） | 不 JOIN 该表 | 一次性令牌，单字段范围 |

### 3.4 权限判定规则

| 规则 | 内容 | 出处 |
| :--- | :------------------------------------------------------------------------------- | :------------------- |
| R1 | 员工以 `pluginId + viewId` 发起查询，中枢从 `ref.view_grant` 校验；未授权一律拒绝 | 产品设计 §2.2、UC-001 |
| R2 | 视图查询只返回聚合与索引字段，明细需二次派工 | 产品设计 §2.2 |
| R3 | 无论通过或拒绝，均写一条视图访问审计 | UC-001 步骤 4 |

### 3.5 已知局限（显式写入需求，不得在实现中隐去）

视图级授权 = 授予该域全部记录，"不得反查单条明细"属约定性约束而非技术强制。补偿：视图仅返回聚合与索引字段、明细需二次派工、全部视图访问入审计（产品设计 §2.2）。此局限在 P1 不通过技术手段消除，需求侧以 REQ-VIEW-003 与 REQ-VIEW-004 承担补偿。

## 4. 功能需求总览与编号规则

### 4.1 编号规则

- 需求编号固定式：`REQ-<域>-<3位>`，域为大写英文缩写，3 位为零填充序号，序号在本域内连续且不复用。
- 域的划分以 `spec/opc-xuanji/usecases.yaml` 的 `requirement` 字段为准（VIEW / TOKEN / CONFLICT / WF / AUDIT / TASK），员工线需求拆到 `docs/员工需求/OPC-SRS-101..111`，主文档只保留跨员工的 EMP 域。
- 非功能需求统一用 `REQ-NFR-<3位>`，序号连续覆盖性能、可靠性、安全合规、可运维性四类。
- 需求编号一旦发布不得改号；废弃需求保留编号并置状态，不复用其序号。

### 4.3 需求状态与变更

需求状态取 `草稿 → 评审稿 → 已批准 → 基线`，与文档 frontmatter 的 `status` 同步推进；进入基线须打 SVN tag 并在 `docs/index.md` 登记。需求变更必须同时更新"验收标准"与 §12 追溯表，不允许只改陈述。

## 5. 中枢平台功能需求（VIEW / TOKEN / CONFLICT）

### 5.1 视图级授权（VIEW）

#### 5.1.1 REQ-VIEW-001 视图级授权查询与拒绝审计

依据：产品设计 §2.2、§8.2；UC-001；api.yaml `queryView`。

**需求陈述**：员工以 `pluginId + viewId` 发起只读查询，中枢从 `ref.view_grant` 校验授权；未授权一律拒绝；无论通过或拒绝都写一条视图访问审计。

**验收标准**：

- **AC-1** 授权通过时返回 200 且 `code=0`、`data.viewId` 等于请求视图，`data.rows` 仅含该视图定义的聚合与索引字段（不含敏感字段）。
- **AC-2** 未在 `ref.view_grant` 登记且状态非生效的 `(pluginId, viewId)` 返回 403，`errorCode=ERR-AUTHZ-001`。
- **AC-3** `viewId` 不在 8 个已登记视图内时返回错误码 `ERR-VIEW-001`。
- **AC-4** 每次查询（含拒绝）在 `audit.audit_log` 恰好新增 1 条 `action=view.query` 记录，含 pluginId、viewId、结果。

追溯：UC-001 / TC-VIEW-001

#### 5.1.2 REQ-VIEW-002 视图清单与员工授权声明

依据：产品设计 §2.2、§2.4、§8.1；`ref.employee_plugin`、`ref.view_grant`。

**需求陈述**：视图清单固定为 8 个；员工插件注册时以 `required_views` 声明所需视图，中枢按 §3.2 表校验；公司档案与 OKR 为全员可见，其余按表授权。

**验收标准**：

- **AC-1** 视图总数为 8 个，ID 与 §3.2 表逐字一致（`view_company_profile`、`view_ar_ap`、`view_project_status`、`view_customer_base`、`view_contract_index`、`view_stock_index`、`view_vehicle_index`、`view_okr`）。
- **AC-2** 任一员工查询 `view_company_profile` 或 `view_okr` 均通过，无需逐条授权登记。
- **AC-3** 未在 `required_views` 中声明的视图，即使该员工在其他视图有授权，也返回 403。
- **AC-4** 员工停用（`enabled=false`）后其全部视图查询返回 403，已落库业务数据不受影响。

追溯：UC-001 / TC-VIEW-001

#### 5.1.3 REQ-VIEW-003 敏感字段不落视图

依据：产品设计 §2.2；架构 §七；`biz.customer_sensitive`、`biz.customer`。

**需求陈述**：客户敏感字段只存在于客户管家私有存储，共享数据层与中枢均不落原始值；`view_customer_base` 只以 `sensitivity_level` 标记敏感级别。

**验收标准**：

- **AC-1** `view_customer_base` 的返回字段集中不存在 `customer_sensitive` 表任何列。
- **AC-2** 视图查询语句不 JOIN `biz.customer_sensitive`，实现侧以参数化 SQL 封装固定列清单。
- **AC-3** 视图返回中每行含 `sensitivity_level`，取值来自 `biz.customer` 的级别字段。
- **AC-4** 对含敏感字段的视图请求（同名视图 + 敏感列筛选条件）返回 403 或忽略该筛选，不返回字段值。

追溯：UC-002 / TC-TOKEN-002

#### 5.1.4 REQ-VIEW-004 跨域明细二次派工（need_detail）

依据：产品设计 §2.2 跨域明细请求；§4.5 项目明细异常；§7 联动矩阵。

**需求陈述**：员工需要业务明细时通过 `need_detail{view, filter, reason}` 请求，中枢校验权限后二次派工给所属员工，明细仅本次上下文可见、不落请求方，并记录审计。

**验收标准**：

- **AC-1** `need_detail` 请求必须以 `view`、`filter`、`reason` 三个字段齐全为受理条件，缺任一字段不受理。
- **AC-2** 受理后由中枢向数据所属员工二次派工，请求方插件上下文中不出现明细原文。
- **AC-3** 审计记录必须含请求方、提供方、filter、返回条数四项。
- **AC-4** 请求视图不在请求方授权表内时，直接拒绝并写审计，不进入二次派工。

追溯：UC-001 / TC-VIEW-001

### 5.2 一次性令牌（TOKEN）

#### 5.2.1 REQ-TOKEN-001 一次性令牌签发与消费

依据：产品设计 §2.2、§8.2；UC-002；api.yaml `issueToken` / `consumeToken`。

**需求陈述**：跨域读取敏感字段时，中枢签发绑定单次任务、单字段范围、有效期 ≤ 5 分钟的令牌；使用一次即失效。

**验收标准**：

- **AC-1** 签发成功返回 201、`code=0`，`data.tokenId` 与 `data.expiresAt` 均非空，且 `expiresAt − 签发时刻 ≤ 300 秒`（api.yaml `ttlSeconds` 上限 300；产品设计 §2.2、§8.2 口径为 ≤ 5 分钟）。
- **AC-2** 首次消费成功返回 200 与 `data.fields`，字段集合为签发时 `fieldScope` 的子集。
- **AC-3** 同一令牌第二次消费返回 409 且 `errorCode=ERR-TOKEN-001`，不再返回任何字段值。
- **AC-4** 令牌以 `ref.token.used` 标记消费状态，消费成功即时置为已用。

追溯：UC-002 / TC-TOKEN-001

#### 5.2.2 REQ-TOKEN-002 令牌范围与有效期约束

依据：产品设计 §2.2、§8.2；api.yaml `IssueTokenRequest`、`ConsumeTokenRequest`。

**需求陈述**：令牌必须同时绑定 `taskId`、`pluginId`、`viewId`、`fieldScope`；有效期不得超上限；消费时必须回带同一 `taskId`。

**验收标准**：

- **AC-1** `taskId`、`pluginId`、`viewId`、`fieldScope` 任一缺失时返回 400 `ERR-TOKEN-001`，不产生令牌记录。
- **AC-2** `ttlSeconds > 300` 返回 400，不签发；不传 `ttlSeconds` 时按签发实现默认值签发且该值不得 > 300。
- **AC-3** 消费请求 `taskId` 与签发记录不一致时返回 409 或 400（同一错误码 `ERR-TOKEN-001`），且令牌保持未消费。
- **AC-4** 过期令牌消费返回 409；令牌表保留 `expires_at`，可据此判定过期而不依赖应用内存。

追溯：UC-002 / TC-TOKEN-002

#### 5.2.3 REQ-TOKEN-003 令牌日志不落敏感值

依据：产品设计 §2.2、§8.2、§8.4；UC-002 步骤 4。

**需求陈述**：令牌签发与消费的审计只记录 token_id、task_id、字段名与结果，不记录字段值；令牌过期或超范围的拒绝同样入审计。

**验收标准**：

- **AC-1** 审计记录中不存在敏感字段的原始值，仅含 `token_id`、`task_id`、字段名清单与结果（成功/失败）。
- **AC-2** 拒绝场景（过期、已使用、范围不符）各写一条审计，含拒绝原因码。
- **AC-3** 令牌记录无法用于反查客户敏感字段值：`ref.token.scope` 只存范围描述，不存值。
- **AC-4** 审计写入失败时本次令牌消费整体失败（不返回字段值），不出现"拿到值但无审计"。

追溯：UC-002 / TC-TOKEN-001

### 5.3 冲突冻结与裁决（CONFLICT）

#### 5.3.1 REQ-CONFLICT-001 冲突登记与冻结

依据：产品设计 §2.3、§8.3；UC-003；api.yaml `openConflict`。

**需求陈述**：两个及以上员工对同一业务事实给出不一致写入或归属时，中枢登记冲突并把冻结单元标记为 `conflict_frozen=true`，被冻结单元不参与汇总计算。

**验收标准**：

- **AC-1** 冲突类型限于 `cost`、`customer`、`stock_batch`、`contract_amount` 四类（api.yaml 枚举），其他类型返回 400 `ERR-CONFLICT-001`。
- **AC-2** 登记成功返回 201、`data.conflictId` 非空、`data.frozen=true`，且对应冻结单元实体上 `conflict_frozen` 置为 true。
- **AC-3** 冻结单元必须四选一且存在：一笔业务事件（台账 + 发票 + 项目引用）、一个客户的一段关系期、一次出入库事件（含冲正链）、一份合同。
- **AC-4** 推送分级：单笔金额 ≥ 月均流水 5% 或涉合同/客户承诺即时推送；其余按小时聚合；22:00–08:00 入次日晨报（截止日 12h 内除外）。

追溯：UC-003 / TC-CONFLICT-001

#### 5.3.2 REQ-CONFLICT-002 汇总口径：总额含冻结 + 脚注

依据：产品设计 §2.3、§8.3；UC-003 步骤 2；§4.4 取数约束。

**需求陈述**：汇总查询不剔除冻结记录，返回 `total_including_frozen` 与 `frozen_items`，由渲染层生成"总额（含冻结）+ 脚注"；不得静默剔除。

**验收标准**：

- **AC-1** 汇总结果同时含总额（含冻结）与被排除事件清单，清单每项含笔数、金额、涉及员工。
- **AC-2** 脚注文案必须写明"待裁决，暂缓计入"，且与总额口径同时出现，不单独输出。
- **AC-3** 归属二选一时，双方报表并列标注，任一方数字不覆盖另一方。
- **AC-4** OKR 取数、月报、联动输出与报表口径一致；OKR 取数遇冻结事件须标注"含 N 笔待裁决事件，暂缓计入"。

追溯：UC-003 / TC-CONFLICT-001

#### 5.3.3 REQ-CONFLICT-003 裁决卡与裁决后处置

依据：产品设计 §2.3、§8.3；UC-003 步骤 3~4；api.yaml `resolveConflict`。

**需求陈述**：老板在裁决卡选择 A / B / manual / later；裁决后清除冻结标记，写 `arbitration_log`，生成受影响报表清单；历史报表不自动重算。

**验收标准**：

- **AC-1** `choice` 仅接受 `A`、`B`、`manual`、`later` 四值；`manual` 时必须带 `manualValue`，否则返回 400 `ERR-CONFLICT-001`。
- **AC-2** `later` 不解除冻结，静默 24 小时后提醒一次。
- **AC-3** 裁决（A/B/manual）后冻结单元 `conflict_frozen` 置回 false，`arbitration_log` 新增 1 条，`ConflictQueue` 记录 `arbitration_id`。
- **AC-4** 裁决返回体含受影响报表清单；历史报表不自动重算，仅在原报表追加"已于 X 日裁决"标注。
- **AC-5** 裁决卡必须呈现冲突类型、冻结单元摘要、双方原始依据，老板无需重新查数据。

追溯：UC-003 / TC-CONFLICT-002

## 6. 流程固化与评判功能需求（WF）

### 6.1 REQ-WF-001 流程注册与六项准入守卫

依据：产品设计 §2.4、§8.6.9.5；UC-004；api.yaml `registerWorkflow`。

**需求陈述**：任何流程注册（含自动注册）前必须通过六项守卫：meta schema、视图授权、幂等完整性、工具合法性、跨员工隔离、代码哈希一致性；失败即拒绝注册，不静默降级。

**验收标准**：

- **AC-1** 守卫项固定六项，缺任一项校验即视为未实现：meta schema 合规、`required_views` 全在授权表内、`idempotent_nodes` 覆盖全部写节点、`agent()` 调用清单在所属员工注册工具内、无其他员工私有数据引用、注册代码哈希 = 测试通过时代码哈希。
- **AC-2** 守卫失败返回 422，响应含 `failures[]`（`item` + `detail` 逐项原因），错误码 `ERR-WF-001`。
- **AC-3** 守卫失败不写入 `ref.workflow_registry`，并写审计知会老板（含具体失败项）。
- **AC-4** 代码哈希不一致时拒绝并要求重跑测试，不接受"内容等价"的人工豁免。
- **AC-5** 注册成功返回 201 与计算出的 `riskLevel`，`status` 为可运行状态。

追溯：UC-004 / TC-WF-001、TC-WF-002

### 6.2 REQ-WF-002 流程实例与幂等节点

依据：产品设计 §8.6.5；UC-005；api.yaml `startInstance` / `completeNode`。

**需求陈述**：写节点以 `instance_id + node_id` 为幂等键执行，中断恢复不重复入库；同键不同入参返回 409 并写审计。

**验收标准**：

- **AC-1** 以已注册版本启动实例返回 201 与 `data.instanceId`；未注册流程或版本不存在返回 404 `ERR-WF-003`。
- **AC-2** 写节点首次执行返回 200、`data.idempotentHit=false`，并记录幂等键、节点状态与输出。
- **AC-3** 同 `(instanceId, nodeId)` 重复提交相同入参返回 200、`data.idempotentHit=true`、输出与首次一致，且不产生第二条业务写入。
- **AC-4** 同幂等键不同入参返回 409 `ERR-WF-004` 并写审计。
- **AC-5** 恢复重跑时已执行节点跳过，流程生命周期事件可完整回放。

追溯：UC-005 / TC-WF-003、TC-WF-004

### 6.3 REQ-WF-003 Verifier 评判与低置信升级

依据：产品设计 §8.6.3、§8.6.6；架构 §3.2、§3.3；UC-006；api.yaml `recordVerdict`。

**需求陈述**：高影响节点（`deadline_impact=true` 或涉金额阈值）三次采样投票；置信度低于阈值（默认 0.8）升级人工裁决；采样均落低分差区间时不自动通过。

**验收标准**：

- **AC-1** 评判记录必须含采样次数、各次 verdict、最终置信度、是否升级人工四项。
- **AC-2** 高影响节点置信度 < 0.8 时 `escalated=true` 并生成裁决卡；不以单次评判或低分差投票结果自动通过。
- **AC-3** `evidence_hash` 命中时返回 `cacheHit=true`，只省去重复调用，结论仍取首次完整采样的 verdict。
- **AC-4** `evidence_hash` 的字段集来自流程 `meta.verifier_policy`：税务取"发票合计、流水合计、差异计数"，补贴取"文号、发布日期、适用期"，库存取"SKU、数量、单价、相对方"。
- **AC-5** Verifier 不可用时节点阻塞，不降级为"默认通过"；按 `deadline_impact` 决定即时或聚合告警，老板可手动放行（强审计）。

追溯：UC-006 / TC-WF-005

### 6.4 REQ-WF-004 风险等级硬规则

依据：产品设计 §8.6.9.5；架构 §七。

**需求陈述**：风险等级由 Registry 按硬规则计算，`meta` 中不允许出现 `risk_level` 字段（防自述）；写入风险按员工插件注册时声明的 `write_targets` 判定，不看流程自述。

**验收标准**：

- **AC-1** 满足任一条件即判高风险：`deadline_impact=true`；流程写入涉及财税、法务、客户敏感字段（按 `write_targets` 判定）；含 `human_gates`；下游有已注册的依赖流程；单次运行涉及金额超过月均流水 5%。
- **AC-2** 提交的 `meta` 含 `risk_level` 字段时拒绝注册（归入 REQ-WF-001 AC-2 的 422 响应），错误项明确标注该字段。
- **AC-3** 任一写工具命中高风险域即整体标记高风险，不因流程声明 `scope:"single"` 而降级。
- **AC-4** 风险等级计算结果写入 `ref.workflow_registry` 并可被看板与告警策略读取。

追溯：UC-004 / TC-WF-002

### 6.5 REQ-WF-005 异常根因诊断与分流

依据：产品设计 §8.6.4；UC-006。

**需求陈述**：Verifier 不通过时由中枢 `opc_hub.diagnose` 定位失败环节；诊断卡输出四项；诊断结论按四类分流处理。

**验收标准**：

- **AC-1** 诊断输入必须含 `verdict`、节点输入输出、上游产出、流程 `meta`、历史同类失败记录五类。
- **AC-2** 诊断卡必须含四项：失败环节定位、证据引用、流程修改建议、影响面评估。
- **AC-3** 四类分流的动作互斥且可判定：数据问题→不改流程版本；流程设计问题→转 coding agent 自动修复任务；外部异常→走 §11.4 降级；不适合固化→终止流程回退技能模式并写经验库。
- **AC-4** 诊断卡作为知会卡（低风险）或观察期异常确认卡（高风险），不作为审批卡；老板不被要求审代码。
- **AC-5** 建议按"流程 ID + 建议类型 + 7 天窗口"聚合，同类问题合并为一次修复任务。

追溯：UC-006 / TC-WF-005

### 6.6 REQ-WF-006 Registry 只读快照与高可用

依据：产品设计 §2.4 Registry 高可用要求、§8.5；架构 §六。

**需求陈述**：每次流程注册/版本变更时导出只读流程快照到本地文件；引擎不可用时从快照生成人工操作清单；`deadline_impact=true` 的流程注册时必须声明降级路径。

**验收标准**：

- **AC-1** 快照内容固定五项：流程定义、节点清单、`deadline_impact`、`human_gates`、降级清单模板。
- **AC-2** `deadline_impact=true` 的流程注册时若未声明降级路径（人工清单模板 + 责任人/联系人），注册被拒绝。
- **AC-3** 引擎不可用时推送人工操作清单，不静默跳过；恢复后由老板决定是否重跑，重跑走幂等校验。
- **AC-4** 快照缺失或过期时即时告警，并拒绝注册新的流程版本。
- **AC-5** P1 阶段完成 Registry 故障演练并留档：引擎不可用 → 快照导出 → 人工清单推送 → 恢复后幂等重跑。

追溯：UC-004 / TC-WF-001

### 6.7 REQ-WF-007 回滚分阶段机制

依据：产品设计 §8.6.9.7、§8.5。

**需求陈述**：自动回滚不是整体撤销，分三阶段——暂停（必做）、评估（自动）、处置（可逆回滚或冻结 + 人工修复）；高影响流程一律不做整体回滚。

**验收标准**：

- **AC-1** 阶段一停止新实例创建并保留已执行记录，可观测到实例创建被阻断。
- **AC-2** 阶段二输出"可逆/不可逆"清单，判定依据为已执行实例是否触发下游动作（开票、回款、台账写入）。
- **AC-3** 可逆时执行回滚脚本；不可逆时转"冻结 + 人工修复"确认卡，卡内含已执行记录与影响面。
- **AC-4** 高风险等级流程只做"暂停 + 人工修复"，不执行整体回滚。
- **AC-5** 自动回滚判定标准固定四条：Verifier 连续 2 次判定不通过；写入被幂等键拒绝或数据层校验拒绝；产出与影子模式基线偏差超阈值；流程执行异常中断且无法恢复。

追溯：UC-004 / TC-WF-001

### 6.8 REQ-WF-008 灰度上线、观察期与流程膨胀治理

依据：产品设计 §8.6.9.6、§8.6.9.8；架构 §3.1。

**需求陈述**：守卫通过后注册新版本并灰度放量；常规流程观察期 20 次或 30 天（先到者），低频流程 5 次或 90 天（先到者）；连续 90 天零实例标记休眠。

**验收标准**：

- **AC-1** 灰度档位为 10% → 50% → 100%，每档观察期默认 3 天；异常按风险等级分别处置（低风险自动回滚并周报知会，高风险推确认卡）。
- **AC-2** 常规流程观察期取"20 次或 30 天先到者"；预估年运行 < 12 次的低频流程取"5 次或 90 天先到者"，看板标注"观察期延长中"。
- **AC-3** 观察期内一直未触发的流程不自动转正，保持观察标记直到达到条件。
- **AC-4** 连续 90 天零实例的流程标记"休眠"，不自动删除、不再出现在看板主视图；唤醒前必须重跑 dry_run。
- **AC-5** 季度输出"可合并流程清单"（流程 ID 相似度 + 节点重叠度）知会老板。

追溯：UC-004 / TC-WF-002

### 6.9 REQ-WF-009 沙箱、三关测试与超时绑定

依据：产品设计 §8.6.9.1~8.6.9.4；架构 §3.1 超时绑定点。

**需求陈述**：coding agent 在隔离沙箱生成与执行，单次执行上限 5 分钟；三关测试的静态检查与历史回放由独立 Verifier Agent 执行；测试数据与真实台账隔离。

**验收标准**：

- **AC-1** 单次执行超时以 `AbortSignal.timeout(300_000)` 绑定到 `WorkflowStartRequest.signal`；超时即视为失败并计入迭代次数。并发上限显式设置：跨员工流程 `maxConcurrentAgents=4`、`maxTotalAgents=50`，不依赖 CPU 自动解析。
- **AC-2** 第一关静态检查与第三关历史回放均由独立 Verifier Agent 执行，与 coding agent 不共用模型配置与上下文，且不接收 coding agent 的自我解释；冲突以 Verifier 为准。
- **AC-3** 历史回放通过标准三条：最小样本量 ≥ 20 条；字段级加权一致率 ≥ 95%；关键字段（金额/数量/相对方）不一致一票否决。
- **AC-4** 自动修复迭代上限 `max_iterations` 默认 5；超限或诊断"不适合流程化"则终止固化，知会卡含失败原因分类 + 可操作建议并写经验库。
- **AC-5** 影子运行周期默认 2 周或 20 个任务实例（先到者），差异率 ≤ 5% 才进入准入守卫；测试数据空间隔离，审计记录标 `test_mode=true`，不计入业务统计。

追溯：UC-004 / TC-WF-001、TC-WF-003

## 7. 审计与归档功能需求（AUDIT）

### 7.1 REQ-AUDIT-001 审计唯一写入口与记录范围

依据：产品设计 §8.4；UC-007；数据库角色对 `audit_log` 只有 INSERT。

**需求陈述**：员工插件不得直写审计库，一律调用 `opc_hub.audit.record({...})` 由中枢统一落库；流程上下文内自动注入 `workflow_instance_id`。

**验收标准**：

- **AC-1** 数据库账号对 `audit_log` 只有 INSERT 权限，无 SELECT/UPDATE/DELETE；员工侧直写尝试失败。
- **AC-2** 记录范围覆盖：派工、工具调用、视图访问、令牌签发与使用、老板确认/裁决、补贴标准确认、技能确认、数据删除、视图授权变更、流程实例生命周期事件、Verifier 评判、诊断卡、流程版本变更、coding agent 生成与修复记录、测试报告、Registry 准入守卫结果、自动回滚事件。
- **AC-3** 流程上下文内的审计自动注入 `workflow_instance_id`，员工插件无感知；非流程场景该字段为 null。
- **AC-4** 支持按 `workflow_instance_id` 聚合导出。
- **AC-5** 每条记录含时间戳、操作人、动作、对象、结果、`schema_version`、`workflow_instance_id`。

追溯：UC-007 / TC-AUDIT-001

### 7.2 REQ-AUDIT-002 哈希链增量导出与链头持久化

依据：产品设计 §8.4；架构 §六、§5.4；UC-007。

**需求陈述**：每日 02:00 增量导出 JSONL，计算全文 SHA-256 与 `prev_hash`，更新 `audit_chain_head`；导出目录只追加不覆盖。

**验收标准**：

- **AC-1** 导出触点为每日 02:00 增量；每月 1 日全量归档。
- **AC-2** 每次导出产出 JSONL + CSV，并生成 SHA-256 校验文件；文件头写入 `schema_version`、上一条文件哈希、本条文件哈希与链头表快照。
- **AC-3** 每次导出后 `audit.audit_chain_head` 更新为本次链头；导出目录结构为 `archive/audit/YYYY/MM/`，只追加不覆盖。
- **AC-4** 审计表按月分区后，导出按分区遍历，不假设单表全量扫描；分区触发条件为审计表约 5000 万行或单库 100GB。
- **AC-5** 审计归档的 `schema_version` 迁移脚本与业务 schema 迁移共用同一迁移链。

追溯：UC-007 / TC-AUDIT-002

### 7.3 REQ-AUDIT-003 保留期、格式与可迁移性

依据：产品设计 §8.4 表格"保留期/可迁移性"；架构 §5.3。

**需求陈述**：会计凭证类 ≥ 30 年，合同类按合同期限 + 5 年，一般操作日志 ≥ 5 年，个人信息删除请求审计单独标记保留；30 年保留项同时输出开放格式 CSV/PDF。

**验收标准**：

- **AC-1** 保留期按四档执行，且每档在归档索引中可查（凭证 30 年、合同期 + 5 年、一般日志 ≥ 5 年、删除请求审计单独标记）。
- **AC-2** 30 年保留项同时输出 CSV 与 PDF（PDF 用 Pandoc + 固定模板），不只存 PG 备份。
- **AC-3** 归档文件头写 `schema_version`；主版本升级须提供迁移脚本，迁移前旧格式保持可读，保留期内至少保留一代读取器。
- **AC-4** 审计归档独立于 PG 备份生命周期，不随数据库备份过期而失效。

追溯：UC-007 / TC-AUDIT-002

### 7.4 REQ-AUDIT-004 恢复一致性校验与失败告警

依据：产品设计 §8.4 失败处理、§8.5；架构 §六；UC-007 步骤 4。

**需求陈述**：恢复时先校验链头表与最后一条导出文件的一致性，不一致则告警并拒绝自动续链；导出失败重试 3 次后即时告警，不静默失败。

**验收标准**：

- **AC-1** 恢复流程第一步比对 `audit_chain_head` 与最后导出文件的哈希；不一致时拒绝续链并告警。
- **AC-2** 导出失败重试 3 次后触发即时 IM 告警；重试次数与告警对象可观测。
- **AC-3** 校验通过的续链不重复写入已导出记录（增量游标可续）。
- **AC-4** 链路校验失败的事件本身写入审计（若审计可写）或触发独立告警通道，不留空白。

追溯：UC-007 / TC-AUDIT-001

## 8. 定时自动化与网页表现层功能需求（TASK / WEB）

### 8.1 REQ-TASK-001 定时任务配置与执行

依据：产品设计 §六 主动智能事件总表；UC-008；api.yaml `listTasks` / `upsertTask` / `runTask`。

**需求陈述**：按公司运营需要增删改定期任务，任务以 `cron + 时区 + 参数` 配置驱动；到点触发，执行结果写 `task_run` 与审计。

**验收标准**：

- **AC-1** `cron` 与 `timezone` 为必填；`cron` 无法解析或任务类型未注册时返回 400 `ERR-TASK-001`，不保存。
- **AC-2** 保存成功返回 `data.nextRunAt`，与 `cron + timezone` 推算一致；`enabled=false` 时不参与调度。
- **AC-3** 任务列表返回每个任务的下次触发时间与最近运行状态。
- **AC-4** 任务不存在时 `run` 返回 404 `ERR-TASK-002`。

追溯：UC-008 / TC-TASK-001

### 8.2 REQ-TASK-002 每日晨报聚合产出

依据：产品设计 §六"每日晨报"、§9；UC-009；api.yaml `getDailyReport`。

**需求陈述**：工作日 08:30 聚合当日待办、到期、冲突与预警，写入 `stat.daily_report` 并可查询。

**验收标准**：

- **AC-1** 触发时间为工作日 08:30；产出写入 `stat.daily_report`（含 `report_date` 与内容）。
- **AC-2** 汇总口径固定五项：税务申报 ≤ 7 天、合同到期 ≤ 30 天、待裁决冲突、低置信升级、观察期异常。
- **AC-3** 按紧急度分级：即时项单独推送，聚合项入晨报；22:00–08:00 的非即时事件入次日晨报，截止日 12h 内提醒豁免夜间静默。
- **AC-4** 查询缺省返回最近一期；尚无晨报返回 404；指定日期无数据同样返回 404。

追溯：UC-009 / TC-TASK-004

### 8.3 REQ-TASK-003 任务幂等、重试与告警

依据：产品设计 §六"审计导出失败"、§8.5；UC-008 步骤 3~4；架构 §2.5。

**需求陈述**：到点触发时按 `scheduled_at` 生成幂等键，重复触发跳过；异常按重试策略处理并写告警通知；不引入消息队列依赖。

**验收标准**：

- **AC-1** 同一 `(taskId, scheduled_at)` 重复触发时第二次返回 `skipped=true`，不产生第二条 `task_run`。
- **AC-2** 手动触发可指定 `scheduledAt` 或 `force=true`；`force` 用于显式绕过幂等，且写审计。
- **AC-3** 执行异常按重试策略处理，最终失败写告警通知（`stat.notification`）并标 `test_mode=false`。
- **AC-4** v1 不部署 Redis，任务幂等与重试不依赖内存或外部队列，重启后由数据库状态恢复。

追溯：UC-008 / TC-TASK-002、TC-TASK-003

### 8.4 网页表现层功能需求（WEB，v2.10 新增）

依据：产品设计第九章；架构第八章；UC-010..UC-014。表现层不新增业务裁决权，所有读取按授权范围，所有写入经中枢确认与审计。

#### 8.4.1 REQ-WEB-001 插件栏入口与右侧面板

**需求陈述**：安装后 DSH 左栏显示“OPC公司管理”入口，点击打开右侧 Web 面板；面板承载驾驶舱、十一域栏目、日报/简报、流程与任务、设置五类页面。

**验收标准**：

- **AC-1** `GET /api/v1/web/manifest` 返回 `pluginId=opc_web`、标题、右栏标识与五个页签；左栏入口与角标数量来自中枢，不由前端自行编造。

#### 8.4.2 REQ-WEB-002 会话桥与记忆桥

**需求陈述**：插件可在老板授权范围内读取中间会话与记忆插件记忆；未授权、超范围或已撤回一律拒绝，不返回空结果伪装成功。

**验收标准**：

- **AC-4** 授权、撤回、上下文读取、记忆检索/提议/确认全部写审计；审计不落敏感值。

#### 8.4.3 REQ-WEB-003 上传/输入归置到十一域

**需求陈述**：老板通过 DSH 上传或输入的信息，经“捕获→分类→抽取→归置卡/收件箱→中枢确认”流水线归置到十一域；高风险域写入必须人工确认。

**验收标准**：

- **AC-1** 归置项保存 `content_hash` 与幂等键；同一内容重复提交返回既有记录，不重复入库。
- **AC-2** 置信度 ≥0.85 且非高风险域归置为 `auto_draft`；0.55–0.85 生成确认卡；<0.55 进入收件箱。
- **AC-3** 财税、法务、客户、库存写入无论置信度高低一律 `confirm`，确认前不写业务表。
- **AC-4** 归置卡展示原文、抽取字段、建议域/写入目标、置信度与来源；确认/忽略均写审计。

**需求陈述**：日志、日报、简报、流程看板、冲突、任务与雷达数据聚合为右栏只读驾驶舱，统一 `as_of`、陈旧提示与冻结脚注。

**验收标准**：

- **AC-1** 驾驶舱查询在只读 `REPEATABLE READ` 事务内完成，返回统一 `as_of`；不 JOIN `customer_sensitive`。
- **AC-2** 冻结冲突按“总额（含冻结）+ 脚注”输出；不填 0 冒充无数据。
- **AC-3** 聚合失败保留上次快照并标 `stale`；数据不足时返回 `warnings`，不猜测填充。
- **AC-4** 90 天查询 p95 ≤500ms（4C/16G 本地）；超时降级为缓存快照。

追溯：UC-012 / TC-WEB-003

#### 8.4.5 REQ-WEB-005 插件雷达与关键词雷达

**需求陈述**：计划任务定期检索适用 DSH 插件与公司发展关键词，只推荐不自动安装，附来源、许可证、权限与风险。

追溯：UC-013 / TC-WEB-004

**需求陈述**：面板访问、会话引用、记忆检索、上传归置、驾驶舱导出与计划任务运行全部纳入权限与审计；敏感字段不上面板。

**验收标准**：

### 9.3 REQ-EMP-002 安装、启用、停用与卸载

**需求陈述**：员工插件可独立安装、启用、停用、卸载；停用后不再派工、工具不可见、单员工流程不启动；卸载默认保留业务数据。

**验收标准**：

- **AC-1** 安装/启用/停用/卸载均写审计（操作人、插件、版本、结果、原因）。
- **AC-2** 停用只改变可用性，不删除业务数据；历史报表仍可读，但不再产生新写入。
- **AC-3** 卸载默认保留 `biz.*` 数据并转只读；删除数据必须老板显式确认并走数据删除审计。
- **AC-4** 停用/卸载不影响其他员工插件；中枢派工队列中被停用的任务转“不可派工”并知会老板。

追溯：`test/integration/employees.test.ts` / AC 直验

### 9.4 REQ-EMP-003 派工隔离与最小权限

**需求陈述**：员工之间不直接调用；跨域读取只经视图，写入经中枢；员工插件只能注册自己声明的工具与单员工流程。

**验收标准**：

- **AC-1** 派工时只注入该员工 manifest 声明的视图与工具；未声明视图请求一律拒绝并写审计。
- **AC-2** 员工不得递归派工；跨域明细只走 `need_detail` 或一次性令牌。
- **AC-3** 写工具必须声明 `write_targets`；Registry 按写目标判风险，不看员工自述。
- **AC-4** 员工插件不得直写 `audit.audit_log`、`ref.token`、`ref.employee_plugin` 等中枢表。

追溯：`test/unit/employees.test.ts` / AC 直验

### 9.5 REQ-EMP-004 版本、兼容与依赖

**需求陈述**：插件版本不可变；升级前校验 `minHubVersion`、`schemaVersion`、依赖插件与视图授权；不兼容时拒绝启用并给出升级路径。

**验收标准**：

- **AC-1** 同 `pluginId + version` 重复安装返回既有记录；版本内容变化必须升版本号。
- **AC-2** `minHubVersion` 高于当前中枢版本时拒绝安装/启用，提示升级中枢。
- **AC-3** 依赖插件未安装/已停用时，导入或启用失败并列出缺失依赖。
- **AC-4** 升级保留旧版本记录与回滚点；高影响升级先 dry-run，不直接覆盖运行中版本。

追溯：AC 直验 / `test/unit/employees.test.ts`

### 9.6 REQ-EMP-005 单员工流程与跨员工流程归属

**需求陈述**：`scope=single` 流程在员工插件注册；`scope=cross` 流程在中枢 Registry 注册；员工插件不得注册引用其他员工私有数据的流程。

**验收标准**：

- **AC-1** 单员工流程的 `owner_plugin` 必须等于 manifest `pluginId`，否则拒绝注册。
- **AC-2** 跨员工流程只在中枢 Registry 注册，员工插件只提供 `agent()` 工具。
- **AC-3** 流程 `required_views` 必须在员工 manifest 声明范围内；Registry 准入守卫二次校验。
- **AC-4** 停用员工插件时，其单员工流程停止新实例；跨员工流程按依赖标注阻塞。

追溯：`OPC-SRS-001` §6 / `test/unit/employees.test.ts`

### 9.7 REQ-EMP-006 员工包导出

**需求陈述**：可把员工插件导出为可移植包，包含 manifest、单员工流程文件、配置 schema、README/CHANGELOG 与校验和；默认不包含业务数据、凭据与客户敏感信息。

**验收标准**：

- **AC-1** 包格式为 `opc-employee-package` v1（JSON 信封），含 `manifest`、`files[]`（path/sha256/contentBase64）、`checksum`，可选 `signature`。
- **AC-2** 默认导出排除 `biz.*` 业务数据、`.env`、令牌、客户敏感字段；导出内容不含密钥。
- **AC-3** 导出文件逐项计算 SHA-256，包级 checksum 覆盖 manifest + files；导出写审计。
- **AC-4** 包可在另一中枢导入；不兼容时导入前拒绝，不产生半安装状态。
- **AC-5** 可选“含数据导出”必须老板显式确认、脱敏并单独标记；默认关闭。

追溯：`test/unit/employees.test.ts` / `test/integration/employees.test.ts`

### 9.8 REQ-EMP-007 员工包导入

**需求陈述**：导入员工包前做格式/校验和/路径/版本/依赖/视图/工具/写目标校验，先 dry-run 展示差异与风险，老板确认后安装为停用状态，再显式启用。

**验收标准**：

- **AC-1** 校验包格式、checksum、manifest schema、`pluginId` 冲突、路径穿越、文件大小/类型、工具与写目标合法性。
- **AC-2** dry-run 输出新增/变更/冲突清单（视图、工具、流程、写目标）、依赖缺失与风险；不产生安装副作用。
- **AC-3** 老板确认后安装，默认 `enabled=false`；启用需二次确认，高风险插件（写财税/法务/客户敏感）强制人工确认。
- **AC-4** 导入失败回滚，不留下半安装插件/流程/授权；失败原因写审计并知会老板。
- **AC-5** 导入不覆盖既有业务数据；同名插件按版本升级/并存策略处理，不静默替换运行中版本。

追溯：`test/integration/employees.test.ts` / AC 直验

测试用例编号采用 `TC-<域>-<3位>`，域与 REQ 域一致。`spec/opc-xuanji/usecases.yaml` 已登记 13 条（TC-VIEW-001、TC-TOKEN-001/002、TC-CONFLICT-001/002、TC-WF-001..005、TC-AUDIT-001/002、TC-TASK-001..004）。表中 TC 列为空的条目，其验收由本章 AC 直接承担，TC 编号随 G3 测试计划按同一规则登记，域内序号不与被登记条目冲突。

## 13. 术语与口径

| 术语 | 口径 | 出处 |
| :------------------------ | :----------------------------------------------------------------------------- | :------------------- |
| 视图级授权 | 授权粒度 = 视图，不做字段级；"不得反查单条明细"为约定性约束 | 产品设计 §2.2 |
| 一次性令牌 | 绑定单次任务 + 单字段范围，有效期 ≤ 5 分钟，使用一次即失效 | 产品设计 §2.2、§8.2 |
| 冻结单元 | 最适宜老板评判的业务事件：一笔业务事件 / 一段客户关系期 / 一次出入库事件 / 一份合同 | 产品设计 §2.3 |
| 总额（含冻结） | 汇总不剔除冻结记录，返回总额与被排除事件脚注 | 产品设计 §2.3、§8.3 |
| 准入守卫 | 注册前的六项校验：meta schema、视图授权、幂等完整性、工具合法性、跨员工隔离、代码哈希 | 产品设计 §2.4 |
| 硬规则风险等级 | 五条件任一即高风险，Registry 计算，`meta` 禁 `risk_level` | 产品设计 §8.6.9.5 |
| `deadline_impact` | `true`=停滞即在 N 天内影响法定/合同截止日；`false` 须声明 `indirect_deadline` | 产品设计 §8.6.8 |
| evidence_hash | 参与判定结论的关键字段集合的哈希；命中只省调用不改结论 | 架构 §3.2 |
| 影子运行 | 与技能模式并行一个周期（默认 2 周或 20 个任务实例，先到者），差异率 ≤ 5% 才进入守卫 | 产品设计 §8.6.9.4 |
| `test_mode` | 测试数据空间的审计标记，不计入业务统计 | 产品设计 §8.6.9.9 |
| 独立 Verifier Agent | 与 coding agent 不共用模型配置与上下文，只收代码+用例+历史产出 | 产品设计 §8.6.9.2 |
